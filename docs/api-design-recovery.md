# B2.2：共享 API 协调与有限修复

Stage 06 的共享接口更新会重新校验以前的需求。若两个需求的写入边界不同，反复修改同一接口可能交替触发“多写字段”和“漏写字段”；模型输出缺少根字段或引用未知 API 也会消耗重试。

## 处理机制

- 初始任务包含检索到的 API 的所属需求、已接受写入字段、所属需求写入边界，以及是否适合当前需求。API ID 清单包含全部已接受 ID。
- 错误反馈同时提供当前需求和受影响需求的原始场景、读写义务与既有绑定。模型需要保留共享操作，选择或设计由场景支持的兼容操作；不自动修改义务，不推断缺失关联。
- 接受前检查 `apis` / `requirement_apis`、完整接口记录、请求与响应基本结构、未知引用和重复 method/path。不同 API ID 不能绕过同一端点的一致性检查。
- 相同错误第二次出现时，要求从原始任务和已接受契约重新规划，不再把同一个错误答案作为输出模板；第三次仍失败则明确终止该任务。交替出现的错误分别计数。
- 每个需求最多 6 个候选提案、8 次逻辑模型调用（含上下文查询）。SDK 传输重试不包含在该计数中。
- 失败候选不更新正式 API 产物或共享 convention。邻近任务继续执行；失败通过原有 `TaskFailures` 和编译报告保留，不能记作通过。

精确写入边界、旧需求覆盖、场景读写覆盖、数据库字段校验，以及后续 HTTP/浏览器验收均保持启用。契约冲突不能通过简单放宽校验解决。

## 配置与复现

默认随 `b2` profile 开启；`ARC_B2_API_COORDINATION=0` 关闭此层。`b0` / `b1` 不默认启用。

```sh
uv run python -m unittest discover -s tests -p test_api_coordination.py -v
uv run python -m unittest discover -s tests -p test_backend_contracts.py -v
uv run python team-tools/package-baseline.py --variant B2.2
```

回归检查运行真实 Stage 06 接受与持久化流程，模型响应为脚本数据，不调用真实模型。覆盖共享写入冲突恢复、缺字段恢复、重新规划、交替错误停滞、失败隔离、重复端点和上下文调用预算。它不证明真实模型一定能完成重规划，也不代表官方分数或全任务提速。

该版本仍使用固定外层编译顺序。不能自动回到上游重做错误的义务推断；无法解决的矛盾会记录失败。较小的调用预算可能提前终止复杂的有效设计，需要通过平台对照检查质量与费用。
