# 优化计划与两周里程碑

## 核心问题

主线选择：**需求追踪驱动的局部修复 + 受控成本优化**。先用数据定位失败，再挑一至两个改进验证。交互式需求澄清作为后续扩展，避免在两周内同时重写整个系统。

上游已经有 13 阶段、BM25 检索、文件工具、约定存储、测试及自动修复；不能把这些现成功能直接当作本组创新。具体代码位置见架构文档。

## 按收益和依赖排序

| 优先级/工作 | 假设与实施点 | 验证方法 | 完成条件 |
|---|---|---|---|
| P0 基线与合规提交 | 确认任务输入、平台入口和依赖，固定上游 SHA、模型及预算 | 清洁环境跑通一次生成、启动和平台评测 | 有 run_id、包 SHA256、正式成绩链接；失败也保存证据 |
| P0 失败分类与可观测性 | 阶段日志还不足以解释官方失败；建立需求→契约→代码→验收证据映射 | 手工标注首轮全部失败，统计类别和耗时/token 热点 | 每个失败归属需求、阶段、原因和修复建议 |
| P1 需求追踪和覆盖检查 | 部分失败可能来自跨层遗漏；在已有中间产物上补关联，避免另建不兼容格式 | 找出缺 API/事件/状态断言的需求，先补 1–2 个高频类别 | 映射可查；关键链路有从 UI 到持久化的独立验收 |
| P1 定向修复与预算控制 | 失败后仅检索相关需求、契约、代码和最短错误证据；限制修复次数 | 基线 vs 局部修复，固定模型/输入/总预算 | 验收无回退，且通过率或稳定性有可解释改善 |
| P2 上下文裁剪与缓存 | 重复图像分析或检索上下文可能浪费 token；先测再选 | 比较缓存命中、总调用数、实际 usage、总成本和全流程耗时 | 同等质量下 token 或耗时下降；无过期缓存误用 |
| P3 交互式澄清 | 对缺失/矛盾需求产出疑问和假设供人确认 | 本地演示，单独记录交互成本 | 无人评测仍可运行；不在平台运行中等待人工输入 |

缓存键必须包含需求、图片、契约、提示词、模型、代码版本及依赖摘要。修复涉及共享契约时重验所有受影响模块。模型分级、混合检索、多智能体调度仅在热点证据充分时再考虑。

## 目标与取舍

基线未知，暂不承诺绝对分数。初始工程目标：V1 在相同预算下通过率不低于 B0；V2 在无明显质量回退时争取 token 或耗时下降 20%。20% 是待检验目标。若不达标，保留证据并回退该优化。任何提分结论同时报告成本、独立重复次数和波动，不以某次最好成绩代替总体结果。
