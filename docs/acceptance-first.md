# B2：以独立验收驱动实现

B2 调整生成工作流，保留 B0/B1 模式用于对照。模型、任务输入和外部评测器不变。

## 工作流变化

| 环节 | 原流程 | B2 |
|---|---|---|
| Stage 11 | 模型逐需求生成交互触发器原型 | 代码连接已有需求、UI 和 API，生成绑定表，不调用模型 |
| Stage 12 | 过程测试生成与实现，再做独立验收生成与修复 | 从原始需求生成一次独立验收，用同一套验收驱动实现 |
| 局部修复 | 重复检查 UI、后端、构建等 | 编译与当前/已接受验收回归优先；跨层完整回归放在最后 |
| 最终验证 | 多处重复执行 | 完整验收、UI、后端、构建统一验证，失败时有受限全局修复 |

Stage 11 保留原有后端读写义务覆盖检查，并检查绑定中引用的 API 与 UI 元素是否存在。绑定表不伪造触发器或业务代码；实际实现直接依据原始需求、UI 设计和 API 契约。

实现修复不能修改测试；独立测试的生成/审查是单独任务。最终验收关闭 fail-fast，并检查每个必需测试文件都有执行用例，避免只有汇总通过数却漏测某个需求。最终修复失败会回滚并重查已恢复的代码，不能发布被拒绝候选的通过结果。

## 其他开销控制

- 精确重复的大段 JSON 容器仅保留一份，其余使用输入内 `$context_ref`；不截断需求或代码。模型结果必须返回正常完整值。
- 受限文件工具的文字示例和 schema 都使用真实允许路径，保留原权限边界。
- 每个文件编辑或设计任务默认最多 16 次逻辑模型调用，包括一次修改轮次内部的读取和语义查询；SDK 传输重试不在这个计数内。达到预算明确记录失败，不记为成功。
- 后端仅新增当前测试、未改动其他文件时，省去测试生成阶段提前执行的历史回归；实现阶段和最终阶段仍执行完整相关回归。已有实现已经通过真实检查时，不再要求模型做一次空修改。

## 配置

默认 `ARC_AGENT_PROFILE=b2`；`b0`/`b1` 使用旧流程。单项开关优先于 profile：

- `ARC_B2_ACCEPTANCE_FIRST`
- `ARC_B2_DIRECT_BINDINGS`（仅与 acceptance-first 一起启用）
- `ARC_B2_CONTEXT_INTERNING`
- `ARC_B2_SCOPED_TOOLS`
- `ARC_B2_TASK_BUDGET`
- `ARC_B2_BACKEND_PRECHECK`

开关值为 `0`/`1`。`ARC_B2_MAX_TASK_CALLS` 设置单任务调用上限。B1 的上下文复用、访问提示和 fail-fast 开关仍可使用。完整基线对照时需清除单项覆盖值。

## 验证与打包

```sh
uv run python -m unittest discover -s tests -p test_b2_execution.py -v
uv run python team-tools/benchmark-b2-context.py
uv run python team-tools/smoke-b2.py
uv run python team-tools/package-baseline.py --variant B2
```

真实应用 smoke 使用脚本化模型，运行 React/Express/SQLite/Chromium，验证测试生成、业务失败、应用修复、最终回归和构建，不调用付费模型。它只验证工作流，不代表完整网站生成质量。上下文实验统计字符数，不能当作实测 Token 或费用。

输出在本地 `releases/`。B0/B1 已交付 ZIP 保持冻结；B1 重新打包需检出其源码版本，不能把 B2 运行代码标为 B1。

## 需平台验证的风险

直接实现减少一层模型规划，可能增加个别需求的实现难度；模型需正确理解输入引用；预算可能提前终止复杂任务；推迟部分检查可能把错误发现推后。B0 的 28/35 是单次基线，B2 是否提分、提速和降费必须使用同任务、同模型的完整平台对照确认。
